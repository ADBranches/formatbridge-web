# LandaFlow Sprint 02

## Property and Tenancy Management

**Sprint duration:** One week  
**Delivery model:** Parallel team delivery through small, reviewable pull requests  
**Deployment target:** JulyHost-compatible, cloud-neutral Docker deployment  
**Cost constraint:** Free-tier, open-source, or self-hosted services only  
**Prerequisite:** Sprint 01 pull request approved and merged, with authentication, organisation isolation, role-based access, CI, and deployment foundations available on the integration branch

---

## 1. Sprint Objective

Deliver the complete property and tenancy foundation required for landlords and property managers to register properties, define rentable units, maintain tenant profiles, create tenancy agreements, assign occupants, preserve supporting documents, and view accurate occupancy information within strict organisation boundaries.

Sprint 02 must extend the existing organisation-isolated architecture without introducing billing, rent collection, payment processing, maintenance workflows, or EFRIS functionality. Those capabilities belong to later sprints.

---

## 2. Sprint Outcomes

At completion:

1. Authorised organisation members can create and manage properties.
2. Properties can contain independently managed rentable units.
3. Tenant profiles can be created without granting application access automatically.
4. Tenancy agreements can connect one organisation, property, unit, and tenant.
5. Agreement lifecycle states are enforced consistently.
6. Double-booking and overlapping active tenancy periods are rejected.
7. Occupancy is derived from verified tenancy records rather than manually entered totals.
8. Supporting agreement documents can be registered through a storage abstraction without committing files to Git.
9. Cross-organisation identifiers cannot expose or modify another organisation's records.
10. Administrative changes generate immutable audit events.
11. Property, unit, tenant, agreement, and occupancy journeys are available in the authenticated web workspace.
12. CI, browser tests, database tests, and production builds pass before review.

## 4. Domain Conventions

### Identifiers

All primary identifiers must use UUIDs generated by PostgreSQL or Prisma-compatible defaults.

### Timestamps

Mutable records must include `createdAt` and `updatedAt`. Archivable business records must include nullable `archivedAt`.

### Money

Any provisional rent or deposit amount captured for agreement reference must be stored as an integer minor-unit value and accompanied by an ISO 4217 currency code. For Uganda Shillings, store whole UGX values because UGX has no commonly used fractional unit. Financial ledger treatment remains deferred to Sprint 03.

### Dates

Agreement start and end dates must use date-only semantics where time-of-day is irrelevant. Database and API handling must prevent timezone conversion from shifting contractual dates.

### Organisation isolation

Every property, unit, tenant, agreement, document, and occupancy query must derive or verify `organisationId`. Client-supplied identifiers alone must never establish access.

### Archival

Properties, units, tenants, and agreements must be archived instead of destructively deleted when historical tenancy or audit records exist.

## 15. Sprint Security Controls

- Every scoped query includes or derives `organisationId`.
- Permissions are enforced by the API, never by interface visibility alone.
- Tenant contact details are excluded from structured logs.
- Agreement documents use generated object keys and validated storage roots.
- Raw storage paths are not accepted from clients.
- Agreement overlap checks execute transactionally.
- Audit events exclude credentials, tokens, and document contents.
- Archived records remain unavailable to normal create-assignment workflows.
- Uploaded files are excluded from Git and development logs.
- All production configuration remains environment-supplied.
